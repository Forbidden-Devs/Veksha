# Решения для следующей версии

Статус: принято 1 августа 2026 года.

Следующая версия Veksha считается новым этапом проекта, а не бесшовным
обновлением текущей тестовой установки.

## Инфраструктура

- Railway больше не является целевой платформой. Конфигурация Railway удалена
  из репозитория, новые деплои туда не выполняются.
- Автоматические CI/CD workflow временно отключены. Перед merge автор изменения
  запускает проверки затронутых компонентов локально.
- Целевой первый runtime — netcup VPS 500 G12 в Nuremberg с Debian 13, Docker
  Compose и Caddy. Образы собираются локально для `linux/amd64`, передаются по
  SSH и запускаются без сборки на VPS.
- Self-hosted Forgejo с Actions можно рассмотреть как один из вариантов, но это
  не принятое решение. Перед выбором нужно отдельно оценить обновления runner,
  изоляцию секретов, резервное копирование, мониторинг и стоимость поддержки.

Предыдущая Railway-инфраструктура остановлена и удалена оператором. Новые
скрипты не содержат Railway integration и не выполняют обращения к платформе.

## Совместимость и данные

- Обратная совместимость HTTP API, схемы базы и локального состояния клиентов
  не является требованием следующей версии.
- Миграция данных текущих тестовых пользователей не разрабатывается. Первый
  запуск новой версии должен использовать новую пустую базу и новые хранилища.
- Клиенты могут потребовать повторной регистрации, повторного входа и очистки
  локального состояния.
- Код совместимости и миграции сохраняется только тогда, когда он упрощает
  разработку новой модели; сам по себе старый контракт не является причиной
  оставлять такой код.

Сброс не выполняется автоматически из приложения или при старте контейнера.
Перед первым новым деплоем оператор должен остановить старую систему, при
необходимости сделать ограниченный по сроку backup, создать пустые хранилища и
только после проверки новой версии отдельно удалить старые данные и секреты.

## Условия возврата автоматизации

CI и деплой возвращаются только после того, как определены:

1. целевая схема компонентов и данных;
2. воспроизводимая локальная сборка и полный набор обязательных проверок;
3. VPS, способ доставки release и секретов, а также процедура rollback;
4. backup/restore, health checks, журналирование и мониторинг;
5. явная процедура первого запуска на пустой базе.

До этого момента `master` не является автоматически развертываемой веткой, а
релизы и проверки выполняются вручную по документации репозитория.
