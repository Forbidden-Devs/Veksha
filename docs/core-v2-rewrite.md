# Независимое переписывание учебного ядра

## Цель

Заменить унаследованное учебное ядро новой реализацией, созданной по
продуктовой спецификации. Сетевые контракты Veksha и пользовательские данные
сохраняются, внутреннее устройство старого ядра не является контрактом.

Этот документ описывает инженерный процесс и происхождение кода. Он не делает
юридических выводов о правах на исходные материалы.

## Граница новой реализации

Чистая доменная часть находится в `veksha-backend/learning_core_v2`. Связь с
OpenAI и существующим хранилищем вынесена в `learning_core_v2_adapters`, а новый
транспортный слой — в модули `api/*_v2.py`. По умолчанию production продолжает
импортировать старые роутеры; каждый новый срез включается независимо.

Модулям `learning_core_v2` запрещено импортировать старые модули:

- `lesson`, `selection`, `training`, `local_translate`;
- `translation_cache`, `db_cache`;
- пакет `llm` и любые его подпакеты;
- API-модули, которые вызывают старое ядро.

Инфраструктура Veksha подключается только через явно определённые порты. В
частности, новое ядро не должно напрямую импортировать FastAPI, базу данных,
OpenAI SDK или глобальную конфигурацию приложения.

## Источник требований

Допустимые источники:

1. Пользовательские сценарии расширения и веб-приложения.
2. Опубликованные HTTP- и WebSocket-контракты.
3. Схема пользовательских данных Veksha.
4. Новые продуктовые решения, зафиксированные в этом документе или ADR.

Недопустимые источники для новой реализации:

- копирование кода, комментариев, промптов и тестовых примеров старого ядра;
- сохранение внутреннего разбиения старых модулей без продуктовой причины;
- перенос случайных эвристик только ради совпадения реализации.

## Первый вертикальный срез: перевод

Вход:

- непустой текст;
- исходный и целевой языки;
- учебный уровень;
- признак двунаправленного режима.

Выход:

- перевод;
- распознанный исходный язык, если он известен;
- классификация результата как одной словарной единицы или фрагмента текста;
- нормализованная словарная форма и транскрипция, если применимо.

Правила первого среза:

- пустой или состоящий только из пробелов текст отклоняется до вызова LLM;
- запись в словарь производится отдельным портом, а не внутри LLM-адаптера;
- пустой перевод не изменяет словарь;
- для одной словарной единицы сохраняется нормализованная форма, а при её
  отсутствии — очищенный исходный текст;
- фраза передаётся словарному порту как наблюдение, без предположений о том,
  какие слова следует извлечь из неё;
- доменный результат не зависит от формата HTTP-ответа.

## Порядок миграции

1. Реализовать и протестировать новый use case без production-интеграции.
2. Написать новые LLM- и Postgres-адаптеры.
3. Добавить API v2 или feature flag на существующий контракт.
4. Запустить внутреннее тестирование и ограниченное переключение.
5. После полного перехода удалить старую реализацию соответствующего среза.

### Feature flag перевода

Новый переводческий роутер выбирается при старте процесса только при
`VEKSHA_CORE_V2_TRANSLATION_ENABLED=1`. По умолчанию флаг выключен. Модель для
нового адаптера задаётся отдельно через `VEKSHA_CORE_V2_TRANSLATION_MODEL`
(значение по умолчанию — `gpt-5.6-luna`), поэтому переключение не меняет модели
остальных функций Veksha.

Во время внутренней проверки необходимо проверить все три контракта:
`/api/translate`, `/api/quick_translate` и `/api/explain`. Операции записи в
словарь нельзя одновременно выполнять через старое и новое ядро.

### Feature flag словарного обогащения

Наполнение вручную добавленной словарной карточки отделено от обычного
перевода и включается через `VEKSHA_CORE_V2_DICTIONARY_ENABLED=1`. Модель
задаётся переменной `VEKSHA_CORE_V2_DICTIONARY_MODEL` (по умолчанию
`gpt-5.6-luna`). Публичные пути `/api/kb_word` и `/api/kb_word_details` и формат
`WordEntryResponse` не меняются.

Новый use case принимает термин, языковую пару, уровень и необязательный
контекст, а возвращает каноническую форму, краткий перевод и транскрипцию.
Пустой термин, неполная языковая пара и пустой перевод отклоняются до записи.
Идентификатор уже сохранённой карточки не переименовывается автоматически:
каноническая форма остаётся результатом домена и может использоваться в
будущей миграции без риска создать дубликат. При ошибке обогащения только что
созданная карточка удаляется, как и в действующем публичном поведении.

Sentence Mining и извлечение слов из многословного текста намеренно не входят
в этот срез и мигрируются отдельно.

### Feature flag Sentence Mining

Новый генератор учебных карточек включается через
`VEKSHA_CORE_V2_SENTENCE_MINING_ENABLED=1`; модель задаётся переменной
`VEKSHA_CORE_V2_SENTENCE_MINING_MODEL` (по умолчанию `gpt-5.6-luna`). Путь
`/api/kb_word_mine`, формат `SentenceMiningCard`, сохранённая конфигурация и
параметр принудительной регенерации не меняются.

Домен получает термин, известный перевод, исходный контекст, языковую пару,
текущий и следующий CEFR-уровни и требуемое число примеров. До записи он
удаляет дубликаты, принимает только примеры двух запрошенных уровней и требует
полный набор переведённых примеров. Карточка также должна содержать непустую
мнемонику и от трёх до пяти уникальных коллокаций. На максимальном уровне C2
обе квоты объединяются в одну группу без ложной отметки `is_higher`.

Сбой или неполный структурированный ответ не заменяет уже сохранённую карточку.
Извлечение слов из многословного текста остаётся отдельным следующим срезом.

### Feature flag тренировок

Новое тренировочное ядро выбирается при старте процесса через
`VEKSHA_CORE_V2_TRAINING_ENABLED=1`. По умолчанию флаг выключен. Модель задаётся
отдельно через `VEKSHA_CORE_V2_TRAINING_MODEL` (по умолчанию
`gpt-5.6-terra`). HTTP- и WebSocket-пути остаются прежними.

Новый WebSocket хранит исходное задание на сервере по `task_id`; поля `word` и
`question`, возвращаемые клиентом, не используются при оценке ответа. Изменение
FSRS выполняется существующим хранилищем только после результатов `correct`,
`vague` или `incorrect`; `garbage` не меняет расписание.

### Feature flag уроков

Новое ядро тематических уроков включается через
`VEKSHA_CORE_V2_LESSON_ENABLED=1`; модель задаётся переменной
`VEKSHA_CORE_V2_LESSON_MODEL` (по умолчанию `gpt-5.6-terra`). Публичные пути
`/api/lesson-topics` и `/api/lesson/ws`, а также формат учебных карточек
сохраняются.

Доменная модель нового среза состоит из темы, учебных модулей, материалов и
попыток. Подготовка сессии сначала завершает уже сохранённые черновые модули,
затем при необходимости расширяет учебный план. Для повторения выбираются
модули с наименьшим уровнем освоения и меньшим числом попыток. Шесть вопросов
равномерно распределяются между выбранными модулями.

Каждый вопрос получает серверный идентификатор и хранится на сервере до
проверки. Присланные клиентом `block_name` и `question` не участвуют в оценке.
Результат `garbage` позволяет повторить ответ и не меняет историю; остальные
результаты накапливаются как новые свидетельства, не стирая прошлую оценку.
Существующий JSON-документ пользователя преобразуется только в адаптере, без
импорта старых моделей в доменное ядро.

Напоминания о незавершённых темах используют `TopicReviewPolicy` нового ядра и
тот же storage-адаптер. Поэтому `api/settings.py` больше не импортирует старый
`lesson.py`, даже когда старый lesson-роутер временно оставлен для отката.

### Feature flag иммерсии

Новый анализатор comprehensible input включается через
`VEKSHA_CORE_V2_IMMERSION_ENABLED=1`. Его модель задаётся отдельно переменной
`VEKSHA_CORE_V2_IMMERSION_MODEL` (по умолчанию `gpt-5.6-luna`). Публичный путь
`POST /api/immersion/analyze`, порядок блоков и формат предложений сохранены;
проверка entitlement `immersion` остаётся на HTTP-границе.

Доменный use case ограничивает число и параллелизм блоков, не вызывает модель
для коротких фрагментов и одинаковой языковой пары, а отказ одного запроса не
ломает анализ остальных блоков. Результат LLM считается черновиком: ядро
принимает только предложения, которые дословно встречаются в исходном блоке в
том же порядке. Неизвестные CEFR-уровни, переводы-эхо и переводы вне диапазона
уровня пользователя или следующей ступени очищаются до ответа клиенту.
Повторные запросы к одинаковому блоку и учебному профилю обслуживает новый
ограниченный process-local TTL-кэш; новый срез не импортирует старый
`db_cache.py`.

## Проверки происхождения

Для каждого изменения обязательны:

- ссылка на продуктовый пункт или ADR в описании коммита/PR;
- тесты поведения и архитектурной границы;
- отсутствие импортов старого ядра;
- итоговый поиск нетривиальных дословных совпадений и ручной разбор находок.

Процент `SequenceMatcher` используется только как сигнал для ручной проверки,
а не как доказательство самостоятельности или заимствования.
